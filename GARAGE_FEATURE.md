# CARVIS Garage

## Product model

Vehicle identification and vehicle collection are separate actions. `POST /api/v1/scans` identifies and stores a scan but never creates a Garage entry and never awards XP. After a catalog match, Android displays a discovery card. Only an explicit **Ajouter au Garage** action calls `POST /api/v1/garage`.

The Garage is a personal, authenticated collection. PostgreSQL/Supabase is the source of truth. Android never substitutes sample vehicles, XP, rarity or statistics when the API is empty or unavailable.

## User flow

1. The authenticated user captures or imports a vehicle image.
2. FastAPI validates it, stores it in private Supabase Storage and obtains a structured Gemini identification.
3. The result is matched to the `vehicles` catalog.
4. Database-owned rarity and the server-side XP preview are returned with the scan.
5. Android presents Add to Garage / Not now / Already in Garage.
6. Add to Garage submits only `vehicle_id` and the owned `scan_id`.
7. The backend validates ownership, computes XP and creates the collection ledger entry transactionally.
8. Android reloads real Garage entries and statistics.

## Database structure

`vehicles` adds `rarity`, `base_xp`, `rarity_score` and optional `market_value`. Rarity is one of COMMON, UNCOMMON, RARE, EPIC or MYTHIC. These values are curated catalog data and are not generated by Gemini.

`garage_entries` stores UUID `id`, `user_id`, `vehicle_id`, optional owned `scan_id`, durable Storage `captured_image_path`, `captured_at`, immutable `xp_earned`, `created_at` and optional `removed_at`. The unique `(user_id, vehicle_id)` constraint is permanent.

Removal is soft. A removed vehicle disappears from the active collection, but its discovery ledger and XP remain. Re-adding reactivates the same entry with zero additional XP, preventing delete/re-add farming.

## API and security

All Garage routes require a valid Supabase Bearer token and use the resolved `UserProfile`. Every list, detail, check, update and delete query includes `user_id`; users cannot access another collection. Client-supplied XP or rarity is rejected. The optional `scan_id` must belong to the user and match the requested vehicle.

Private scan images remain in Supabase Storage. PostgreSQL stores only their object path; each Garage response creates a fresh signed URL. Catalog image URLs are used when no captured scan image exists.

## Duplicate prevention and consistency

The service performs an application check and relies on the database unique constraint for concurrent requests. A repeated request returns the existing entry, `already_collected=true` and `newly_awarded_xp=0`. Database commit/rollback boundaries keep entry creation and its immutable award atomic.

## Redis decision

Garage data and statistics are not cached in Upstash in this version. Collection reads are indexed and user-scoped; avoiding cache invalidation keeps correctness stronger. Existing Upstash caching for AI identification remains unchanged. Redis may be added later only after measurements justify it.

## Android experience

The bottom navigation template remains unchanged. Garage now has a dedicated two-column grid, real signed images, compact rarity labels, collection count, XP, level progress, detail view, retry, loading and empty states. The old overloaded Garage/profile list no longer drives the Garage route; History remains separate.

## Production setup

Run Alembic revision `0002` against Supabase before deploying the API. Then curate rarity, base XP, rarity score and market value for catalog rows. Migration defaults safely classify existing rows as COMMON / 50 XP, but those defaults are not a substitute for catalog curation.
