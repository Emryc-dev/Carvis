# Database guide

PostgreSQL is the durable relational database; Supabase Cloud operates it. SQLAlchemy 2 maps Python classes and relationships to SQL, while Alembic versions schema changes. Run `alembic upgrade head` against the cloud URL—never create a local database for this project.

Relationships: one auth identity maps to one profile; a profile owns many scans and favorites; a scan may match one vehicle and has many AI attempts; a vehicle has many sourced specification sets. A many-row specification design accommodates model-year/market/source disagreement. Favorites are a user-specific join, not a vehicle flag.

Indexes serve auth lookup, catalog identity/search, scan history (`user_id, created_at`), hashes, and foreign keys. Unique constraints prevent duplicate profiles and favorites. Deletes cascade for owned audit data and set a deleted catalog link to null where scan history should remain.

Use Supabase's transaction pooler for normal serverless/scaled API traffic; use a direct connection when a migration operation requires session features the pooler cannot provide. Pooling avoids a database connection per request. SQLAlchemy has an application-side pool and Supabase has a server-side pooler: keep the former small per process so their product does not exhaust the database. `pool_pre_ping` rejects stale connections. Production credentials belong in a secret manager and should be rotated.

Migration workflow: edit models, generate/review a revision, test on a disposable Supabase project, back up, deploy the migration once, then deploy compatible code. Never trust autogenerated destructive operations without review. Use transactions for multi-row writes; the scan service flushes IDs and commits state together.
